# The missing-provider warning is about the judge; generation reports its own need

## Context and Problem Statement

`src/commands/run.ts` degrades to deterministic evals when provider
construction raises, and warns when it does:

```ts
if (!options.deterministicOnly || options.generate === true) {
  console.warn(
    `moose-docevals: provider unavailable — ${e.message}. Running deterministic evals only.`,
  );
}
```

The second clause reads as "…or generation was explicitly requested". Commander
cannot express that. There is no `--generate` flag, only `--no-generate`, and
commander defaults a negated flag's key to `true`, verified against the parser
itself:

```text
run --deterministic-only                 -> { generate: true,  deterministicOnly: true }
run                                      -> { generate: true }
run --deterministic-only --no-generate   -> { generate: false, deterministicOnly: true }
```

So `options.generate === true` held on every invocation that was not
`--no-generate`, and the warning was suppressed only by the accidental pairing
`--deterministic-only --no-generate`. **`moose-docevals run --deterministic-only`
warned about the AI provider it had just been told to skip.** That is this
repository's own dogfood invocation, and the standard one on a runner with no
API key.

There is no spelling of the intended condition. `generate: true` never carries
`getOptionValueSource() === "cli"`, because no flag sets it to `true`; only the
default does.

## Decision Drivers

- **A warning that fires when nothing is wrong trains people to ignore
  warnings**, including the ones that mean something. `--deterministic-only` is
  a request not to use AI; being told the AI is unavailable is noise by
  construction.
- **The condition has to be expressible.** A rule commander cannot represent is
  not a rule, whatever the code says.
- **Generation genuinely does need a provider**, because a `command` eval with
  no `command` has its script generated by the model. So the signal must not
  simply be deleted.
- **Whether generation needs one is not knowable where the provider is built.**
  It depends on whether the corpus holds a command eval with an empty
  `command`, which `runEvals` discovers pages and resolves plans to find out.
- **The engine already reports it, and more loudly.** A generation target with
  no `generateScripts` becomes an `error` result naming the eval, with
  `skipReason: "no command and script generation unavailable (configure a
  provider or run \`moose-docevals generate\`)"`. An `error` result exits 1.

## Considered Options

1. **Warn only when the judge was wanted**: `if (!options.deterministicOnly)`.
2. **Add a real `--generate` flag** so the intended condition becomes
   expressible.
3. **Read commander's option-value source** in the CLI layer and thread an
   explicit "generation was requested" boolean through.
4. **Defer the warning into the engine**, where the generation targets are
   known.
5. **Keep the clause and document the quirk.**

## Decision Outcome

**Option 1 wins.** The warning is about the judge, and only the judge.

The clause is dropped. The line now says exactly what it means: the judge you
asked for could not be constructed, so the run is proceeding without it. That
condition is `!options.deterministicOnly`, which commander represents precisely.

**Generation's own need for a provider is not silenced. It is relocated to
where it can be answered.** Take `--deterministic-only` on a corpus with a
command eval awaiting generation. The engine produces an `error` result against
that eval, naming it and pointing at `moose-docevals generate`, and the run
exits 1. That is strictly stronger than the warning it replaces. It names the
eval rather than the run, and it appears in `--format json`, SARIF and JUnit
rather than only on stderr. It fails the build rather than scrolling past. On a
corpus with **nothing** to generate, there is nothing to say, and the previous
behavior was saying it anyway.

The resulting table is the whole contract:

| Invocation | Provider unavailable | Behavior |
|---|---|---|
| `run` | yes | warn, run deterministic evals |
| `run --no-generate` | yes | warn, run deterministic evals |
| `run --deterministic-only` | yes | silent |
| `run --deterministic-only --no-generate` | yes | silent |
| `run --ai-only` | yes | exit 2 (`DocevalsError`, unchanged) |
| any | no | silent |

Note that `--no-generate` alone still warns. Turning generation off does not
turn the judge off, and that row is the guard against "fixing" this by deleting
the warning altogether.

### Consequences

- **`moose-docevals run --deterministic-only` is quiet on a keyless runner**,
  which is what it always should have been and what every CI example in the
  docs invokes.
- **A run that needed a provider for generation and did not get one still
  fails**, with a better message than before, attributed to the eval.
- Good, because the surviving condition is one commander can express, so the
  code and the intent cannot drift apart again.
- Bad, because `--deterministic-only` on a corpus with nothing to generate now
  gives no indication that a provider was attempted and failed. That is
  deliberate: the flag says not to use one. `--format json`'s skip reasons still
  record `judge skipped (--deterministic-only)` per eval.
- Neutral, because no exit code changes for any invocation. `--ai-only` still
  exits 2, and the engine's generation error still exits 1.

### Confirmation

`test/unit/provider-warning.test.ts` pins every row of the table above as a
separate case, with `console.warn` spied and `ANTHROPIC_API_KEY` deleted so each
travels the real `makeProvider` failure path.

The test helper builds **the options object `src/cli.ts` actually passes**,
including `generate: true`. That is not incidental. A hand-built call leaves
`generate` as `undefined`, the broken clause tested `=== true`, and the defect
does not reproduce at all. The first draft of this test passed against the
unfixed code. The comment in the file says so, because the next person to
simplify that helper will reintroduce a vacuous test.

A final case pins the replacement signal: `--deterministic-only` over a corpus
holding a command eval with no command errors that eval, names
`configure a provider`, and exits 1.

`.github/workflows/ci.yml` asserts through the built CLI, where commander's
defaults are real, that `run --deterministic-only` on the fixture corpus emits
no `provider unavailable` line. `ANTHROPIC_API_KEY` is explicitly empty there,
so the step cannot pass by a key being present.

## Pros and Cons of the Options

### Option 1, warn only when the judge was wanted

- Good, because the condition is expressible, minimal, and matches what the
  sentence says.
- Good, because it deletes no signal: the generation case moves to a louder,
  better-attributed report.
- Bad, because a provider misconfiguration is now invisible under
  `--deterministic-only` when nothing needs generating. That is acceptable,
  because the flag asked for it.

### Option 2, add a real `--generate` flag

- Good, because it makes "generation was explicitly requested" a thing a user
  can actually say, which is what the original code wanted.
- Bad, because CLAUDE.md requires every CLI flag to have a matching config
  field. This drags a `scripts.generate` key, a schema entry, a default in
  `parseConfig` and its own precedence story along with it. That is a config
  surface added to fix a warning.
- Bad, because it still would not answer the real question. `--generate` means
  "do not disable generation", not "there is something to generate", so the
  warning would still fire on a corpus with nothing to generate.

### Option 3, read commander's option-value source

- Good, because it needs no new flag and the CLI layer is a legitimate place to
  read parser state.
- Bad, because it does not work: nothing sets `generate` to `true` from the
  command line, so the source is always `"default"` for the value that matters.
- Bad, because it would add a CLI-only input to `runRun`, which is also a
  library entry point. A library caller could not reach the same behavior.

### Option 4, defer the warning into the engine

- Good, because the engine is where the generation targets are known, so the
  warning could be exactly right.
- Bad, because the engine already reports precisely this, as an `error` result
  that exits 1. Adding a warning beside it is a second, weaker say-so about one
  condition.
- Bad, because the engine must not read CLI concerns; it receives
  `generateScripts` as an injected function and has no business knowing why it
  is absent.

### Option 5, keep the clause and document the quirk

- Good, because it is no work.
- Bad, because the documented behavior would be "the warning is suppressed by a
  flag combination unrelated to what it warns about". Nobody would rely on that,
  and everybody would eventually re-break it.
- Bad, because the noise falls on the exact invocation the docs recommend for
  CI. That is the population most likely to learn to ignore the tool's output.
