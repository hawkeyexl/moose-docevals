---
title: Named evals and suites
description: Turn per-page assertions into a shared library, and measure page types against a target pass rate.
---

The gate worked on one page, so it got copied. Now the same assertion exists in twelve pages with
three slightly different wordings and nobody can say what a how-to page is actually checked for.

This is where moose-docevals stops being a linter and becomes a standard.

## Name the eval once

Move it into `moose.config.yaml` under `evals`:

```yaml
docevals:
  evals:
    no-future-promises:
      type: regression
      assertion: The page makes no claims about unreleased or future functionality.
      grader: ai
      evidence: All prose sections
      examples:
        pass: Describes only shipped behavior.
        fail: Says "coming soon" or references an unreleased version.
```

Pages reference it by name:

```yaml
evals:
  - use: no-future-promises
```

Change the wording in one place and every page that uses it changes. Names match
`^[a-z0-9][a-z0-9-]*$`.

## Group them into suites

A suite is a named group plus a target pass rate — the checks that apply to a *kind* of page.

```yaml
docevals:
  suites:
    reference:
      target-pass-rate: 1.0
      evals: [no-future-promises, fresh-enough, readable, frontmatter-valid]
    tutorial:
      target-pass-rate: 0.7
      evals: [explains-why-before-how, no-future-promises]
    how-to:
      target-pass-rate: 1.0
      evals: [no-future-promises, readable]
```

```yaml
---
title: Installation
eval-suite: how-to
---
```

Set `defaults.suite` to apply one to every page that names none, and pages only carry an `evals` key
when they need something specific.

## `target-pass-rate` is a suite property

This is the piece people miss, and missing it makes moose-docevals look far too strict.

Individual verdicts are binary. The nuance lives in the **rate across a suite**:

- **1.0** for a regression suite — these checks must all hold.
- **~0.7** for a capability suite — this measures how far a quality goal has spread, and a corpus
  partway there is the expected state, not a failure.

```console
Suites
  reference: 2/3 passed — 67% vs target 100% below target (1 skipped)
```

A suite below target fails the run. Treating a capability finding as a build break — because the
suite was left at the default 1.0 — is the most common way to conclude the tool is unusable.

Skipped evals are excluded from the denominator: `passed / (total - skipped)`.

## Referential integrity is checked at load

Two mistakes fail immediately with exit 2 rather than surfacing later as a confusing per-page
problem:

- A suite referencing an eval that is not defined.
- `defaults.suite` naming a suite that does not exist.

## Narrow without forking

When one page needs a variant, override at the reference rather than defining a near-duplicate:

```yaml
evals:
  - use: fresh-enough
    severity: warning
    options: { max-age-days: 180 }
```

`options` merges over the base; `type`, `severity`, and `skip` replace. A second eval with the id
`fresh-enough-but-stricter` is how a library rots.

## Check what resolved

Suites, references, and inline definitions can all contribute the same name, and **page entries win
on collision**. Do not guess:

```bash
npx moose-docevals list docs/
```

```console
test/fixtures/pages/docs/actions/goTo.mdx (suite: reference)
  - no-future-promises [ai, regression, config]
  - fresh-enough [tool:freshness, regression, config]
  - readable [tool:reading-level, regression, config]
  - frontmatter-valid [tool:docmeta, regression, config]

1 pages, 4 evals resolved
```

`source` — the third item — is `config` or `page`, which is exactly what you need when one page
behaves unlike its neighbours.
