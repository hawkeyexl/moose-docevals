Every eval declaration lives under the `evals` key in page frontmatter. This page is the contract;
[Frontmatter reference](/moose-docevals/reference/frontmatter/) is the exhaustive field list.

## The minimum

The array form is just the eval list:

```yaml
---
title: Concepts
evals:
  - no-future-promises
  - name: defines-core-terms
    assertion: The page defines every core concept it introduces.
---
```

Use the object form when you need a suite or a page-level skip:

```yaml
---
title: Installation
evals:
  suite: how-to
  evals:
    - no-future-promises
---
```

```yaml
---
title: Index
evals:
  skip: true
---
```

## Three ways to name an eval

**Reference a named eval** from `moose.config.yaml` by bare string:

```yaml
evals:
  - no-future-promises
```

**Reference with overrides**, to narrow it for this page only:

```yaml
evals:
  - use: fresh-enough
    severity: warning
    options: { maxAgeDays: 180 }
```

`options` **merges** over the base rather than replacing it, so you can change one setting without
restating the rest. `type`, `severity`, and `skip` replace.

**Define one inline**, when it exists only on this page:

```yaml
evals:
  - name: install-command-present
    assertion: The page contains a bash code block with `npm i -g doc-detective`.
    grader: command
```

Inline evals need a `name`. Everything else is optional — `grader` defaults to `llm` and `type` to
`regression`.

## Prefer named evals

An assertion pasted into twelve pages drifts into twelve slightly different assertions, and nobody
can then say what a how-to page is checked for. Move anything used more than once into the config and
reference it. See [Named evals and suites](/moose-docevals/evals/named-evals-and-suites/).

Inline is right for something genuinely specific to one page — like the exact install command above.

## What wins

The plan is built suite-first, then page entries in document order. **Page entries win on name
collision** — local override beats global default.

That is the correct default and completely invisible until it surprises you, so check rather than
guess:

```bash
npx moose-docevals list docs/installation.mdx
```

```console
test/fixtures/pages/docs/actions/goTo.mdx (suite: reference)
  - no-future-promises [llm, regression, config]
  - fresh-enough [tool:freshness, regression, config]
  - readable [tool:reading-level, regression, config]
  - frontmatter-valid [tool:docmeta, regression, config]

1 pages, 4 evals resolved
```

Each line is `name [grader, type, source]`. `source` tells you whether the definition came from the
config or the page — which is exactly what you need when a page behaves differently from its
neighbours.

## Problems are reported, not thrown

A malformed page does not stop the run. Unknown suite names, unknown eval references, and
schema-invalid frontmatter are reported as page errors with a source line; duplicate names and
inline llm evals missing `examples` are warnings.

Validate the declarations themselves as an eval, so bad frontmatter fails like any other check —
see [Frontmatter reference](/moose-docevals/reference/frontmatter/#validating-the-frontmatter-itself).
