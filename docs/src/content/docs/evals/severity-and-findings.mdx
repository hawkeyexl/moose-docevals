title: Severity and findings
description: What fails the build, what only reports, and how to ratchet a check up over time.
---

Deterministic graders produce **findings**. Severity decides which of them fail the build — and it is
the mechanism behind adopting a new check without breaking everyone.

## Only `error` fails

| Severity | Reported | Fails the eval |
|---|---|---|
| `error` | Yes | **Yes** |
| `warning` | Yes | No |
| `info` | Yes | No |

An eval fails only if it produced at least one `error`-severity finding. `warning` and `info` show up
in the report and in PR annotations, and pass.

```yaml
docevals:
  evals:
    markdownlint:
      assertion: Page passes markdownlint rules.
      grader: tool:markdownlint
      severity: warning        # reports, does not block
    frontmatter-valid:
      assertion: Page frontmatter validates.
      grader: tool:docmeta
      severity: error          # blocks
```

`severity` defaults to `error`.

## The ratchet

This is what severity is *for*. Adding an honest check to an existing corpus fails a lot of pages at
once — accurate and useless, since nobody can merge it.

The move is **not** to weaken the assertion. It is to lower the severity:

1. Add the check at `severity: warning`. It reports on every page; nothing blocks.
2. Burn down the findings, section by section.
3. Flip to `severity: error`. Now it holds.

Weakening the assertion instead permanently encodes the corpus's current state as your standard, and
nobody ever tightens it back. Full sequencing in
[Retrofit a legacy corpus](/moose-docevals/adopt/retrofit-a-legacy-corpus/).

You can ratchet per page while you work, using an override:

```yaml
evals:
  - use: readable
    severity: error          # this section is done; hold the line here
```

## Mapping a tool's own severities

Tools have their own vocabulary. `severityMap` translates it:

```yaml
  style:
    grader: tool:vale
    severityMap:
      error: error
      warning: warning
      suggestion: info       # Vale suggestions report but never block
```

Vale defaults to exactly that mapping. Any tool severity you do not map falls back to `warning`.

## What a finding carries

```console
  FAIL fresh-enough
       error:4 [freshness/stale] Page last reviewed 937 days ago (max 365)
```

`severity:line [ruleId] message`. In JSON:

```json
{
  "evalName": "fresh-enough",
  "file": "docs/actions/goTo.mdx",
  "ruleId": "freshness/stale",
  "message": "Page last reviewed 937 days ago (max 365)",
  "severity": "error",
  "line": 4
}
```

`ruleId`, `line`, and `col` are present when the grader can supply them — most tool graders can,
which is what makes `--format github` able to annotate the exact line.

Severity also maps onto annotation levels: `error` → `::error`, `warning` → `::warning`, `info` →
`::notice`. See [Output and exit codes](/moose-docevals/reference/output-and-exit-codes/).

## Severity is not the LLM's

Severity applies to deterministic graders. A judged eval's outcome comes from consensus and
confidence zones instead — see [How judging works](/moose-docevals/judge/). The capability suite target is
the judged analog of the ratchet; see
[Regression vs capability](/moose-docevals/evals/regression-vs-capability/).
