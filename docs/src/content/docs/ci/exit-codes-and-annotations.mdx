Three exit codes, and the distinction between two of them is the difference between a check people
trust and one they route around.

## The contract

| Code | Meaning | Whose problem |
|---|---|---|
| `0` | Everything passed | — |
| `1` | Findings, errors, or a suite below its target pass rate | The page author |
| `2` | Operational or usage error — bad config, missing provider, malformed flag | The pipeline owner |

## Never collapse `1` and `2`

A recipe like this is wrong:

```yaml
- run: npx moose-docevals run || echo "docs check failed"
```

So is anything that reports every non-zero exit as "the docs are bad". When the provider key is
missing or the config has a typo, exit `2` fires — and blaming the author for it is precisely how a
check earns a reputation for flakiness it does not deserve. Two or three of those and someone removes
the step.

Route them separately:

```yaml
      - id: moose-docevals
        id: moose-docevals
        continue-on-error: true
        run: npx moose-docevals run --format github

      - id: Fail the PR on findings
        if: steps.moose-docevals.outcome == 'failure'
        run: |
          code=${{ steps.moose-docevals.outputs.exit-code || '1' }}
          if [ "$code" = "2" ]; then
            echo "::error::moose-docevals could not run — this is a pipeline problem, not a docs problem."
          fi
          exit 1
```

Simplest correct version: let the step fail naturally, and make sure whoever triages CI knows `2`
means "look at the config, not the page".

## `--fail-on-review`

By default, evals in the human-review zone do not fail the build. With `--fail-on-review`, they exit
`1`.

This is a genuine policy fork, not a best practice:

| | Blocks on review | Doesn't block |
|---|---|---|
| The queue | Never ignored | Can rot |
| Pull requests | Sometimes wait on a person | Keep moving |
| Needs | Someone who owns the queue | — |

The deciding question is whether anyone owns the review queue. If nobody does, blocking on it just
converts a rotting queue into blocked contributors. See
[Human review](/moose-docevals/judge/human-review/).

## Inline annotations

`--format github` emits workflow commands before the markdown summary, so one invocation both
annotates the diff and produces a job summary.

```text
::error file=docs/actions/goTo.mdx,line=4,title=moose-docevals%3A fresh-enough::Page last reviewed 937 days ago (max 365)
```

Severity maps to the annotation level:

| Finding severity | Annotation |
|---|---|
| `error` | `::error` |
| `warning` | `::warning` |
| `info` | `::notice` |

Values are escaped per GitHub's rules — `%`, CR and LF in data; additionally `:` and `,` in
properties, which is why the title renders as `moose-docevals%3A fresh-enough`.

### Judged failures annotate the file

An ai eval has no line to point at, so it annotates the file with the mean confidence and the
judge's reasoning:

```text
::error file=docs/tutorial.mdx,title=moose-docevals%3A no-future-promises::AI judge: fail (confidence 0.93). <reasoning>
```

That reasoning is what a contributor acts on. It is only as good as the assertion behind it — see
[Write good assertions](/moose-docevals/evals/write-good-assertions/).

## Suites below target fail the run

```console
Suites
  reference: 2/3 passed — 67% vs target 100% below target (1 skipped)
```

Exit `1`, even if no individual eval errored. A capability suite left at the default target of `1.0`
is the most common cause of a surprising red build — see
[Regression vs capability](/moose-docevals/evals/regression-vs-capability/).

### A filtered run is not a gate

`--eval` and `--suite` narrow a run to named evals. They are local debugging flags, and they are not
a CI invocation: **while either is active, suite targets are reported but not enforced.**

```console
Suites
  reference: 4/4 passed — 100% vs target 100% partial — filtered run, target not evaluated
```

That is deliberate. A run narrowed to one passing eval out of a suite of twelve would otherwise
compute `1/1 = 100%`, clear a target of `1.0`, and exit `0` having checked almost nothing — a green
check indistinguishable from a real one. So a job built around `moose-docevals run --eval …` does not
get a faster gate; it gives the gate up, on every suite line of its own report.

A filter that matches nothing exits `2` rather than `0`, which is the right routing: an eval renamed
out from under a pipeline is the pipeline owner's problem, and it stops the job instead of passing
it.

Full behavior in
[Selecting evals suspends suite enforcement](/moose-docevals/reference/cli/#selecting-evals-suspends-suite-enforcement).
