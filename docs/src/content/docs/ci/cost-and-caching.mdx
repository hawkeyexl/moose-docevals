---
title: Cost and caching
description: Hard spend ceilings, what invalidates a cached verdict, and why cache persistence is a correctness concern.
---

Model spend is per-invocation, so the risk is not one large bill — it is an *unpredictable* one. And
unpredictable is what gets a check removed.

Two mechanisms make the steady-state cost of a docs pull request approximately zero.

## Hard ceilings that abort

```yaml
docevals:
  judge:
    max-cost-usd: 2.0
  fill:
    max-cost-usd: 5.0
```

```bash
npx moose-docevals run --max-cost 2
npx moose-docevals fill --max-cost 5
```

These **abort the run**; they are not warnings. `null` (the default) means no ceiling.

Set one even when you are confident. The run you regret is the one you did not bound — a config
mistake that widens `files.include`, or a prompt change that invalidates every cached verdict at
once.

## Content-addressed caching

An unchanged page with an unchanged assertion never re-judges. The cache key is composed from,
among other things:

- `PROMPT_VERSION` — the judge prompt revision
- a hash of the **page body**
- a hash of the eval fingerprint — assertion, evidence, examples, type
- the provider and model

So the cache invalidates exactly when a verdict could legitimately differ, and not otherwise. Edit
prose and that page re-judges; edit an assertion and every page using it re-judges; pin a new model
and everything re-judges.

`fill` caches raw proposals **before** the confidence gate, keyed with `FILL_PROMPT_VERSION` — which
is why re-running at a different `--confidence` costs nothing.

| Path | Default | Commit? |
|---|---|---|
| `judge.cache-dir` | `.moose-docevals/cache` | No |
| `fill.cache-dir` | `.moose-docevals/cache/fill` | No |

## Cache persistence is a correctness concern

The cost model assumes repeat runs are nearly free. A CI job that starts cold every time re-judges
the entire corpus on every push, and the resulting bill is the reason someone deletes the step.

```yaml
      - uses: actions/cache@v4
        with:
          path: .moose-docevals/cache
          key: moose-docevals-${{ hashFiles('moose.config.yaml') }}-${{ github.sha }}
          restore-keys: moose-docevals-${{ hashFiles('moose.config.yaml') }}-
```

The config hash belongs in the key: changing an assertion should invalidate verdicts, and this makes
that visible rather than relying on the content hash alone. `restore-keys` lets a new commit start
from the previous run's cache instead of nothing.

## Read the cost

```json
"cost": { "totalUsd": 0.0212, "totalTokens": 18442, "cachedEvals": 214, "judgedEvals": 3 }
```

`cachedEvals` versus `judgedEvals` is the number to watch. On a healthy repo, a docs pull request
judges only the pages it touched. If `judgedEvals` is large on a small diff, something is
invalidating the cache — usually a changed assertion, a model bump, or a cache that is not
persisting.

## Reduce what you spend, not just what you cap

**Push evals down the hierarchy.** The ratio of deterministic to judged evals decides whether the
gate is affordable at ten times the corpus size. See
[Promote to deterministic](/moose-docevals/adopt/promote-to-deterministic/).

**Scope the trigger.** Only run on pull requests that touch docs:

```yaml
on:
  pull_request:
    paths: ["docs/**", "moose.config.yaml"]
```

**Run deterministic on every push, judged on pull requests.** `--deterministic-only` costs nothing
and catches most regressions.

**Lower `judge.ensemble-runs` deliberately, or not at all.** Three runs is the calibrated default;
dropping to one saves two thirds of the cost and removes the consensus signal that makes the
human-review zone meaningful. Measure with [calibrate](/moose-docevals/judge/calibrate/) before you decide
that trade is worth it.

## `--no-cache`

Bypasses the cache for a run. Useful when you have changed a prompt or are debugging a verdict, and
expensive by definition — not something to leave in a CI recipe.
