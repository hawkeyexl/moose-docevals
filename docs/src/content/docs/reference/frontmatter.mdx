Eval declarations live in page frontmatter under four keys, and citations under two more,
validated by the JSON Schema this package publishes at `schemas/frontmatter-1.2.0.json`. That
schema implements `docmeta:evals:1.0.0-proposal.2`, the common vocabulary docmeta proposes for
per-page quality assertions. It also carries the citations vocabulary this package ships ahead of a
docmeta proposal for it. docmeta publishes the vocabulary, and moose-docevals implements the graders behind
it. Older schema versions stay published and byte-identical; a page valid against one is valid
against this. Verified against that schema and `src/core/resolve.ts`.

## The page keys

Settings are page-level facts, not an enclosing object. The page root stays open, so a sibling
tool's keys pass untouched. But the **`eval-` and `cite-` prefixes are reserved**: an unrecognized
`eval-*` or `cite-*` key is an error, not something silently ignored.

| Key | Type | Meaning |
|---|---|---|
| `evals` | string, or non-empty list | One assertion, or the list of entries |
| `eval-suite` | string | Named suite from the config whose evals apply. An unknown name is a page error. |
| `eval-skip` | boolean (`false`) | Skip this page entirely; it reports as skipped. |
| `eval-provenance` | list | The machine-proposal trail `fill` writes. See below. |
| `cites` | non-empty list | Source ranges the page depends on, pinned by hash. See [`cites`](#cites). |
| `cite-commit` | string | Default `commit` for every `cites` entry that omits its own. |

The page's own top-level `generated-by`, which is not an `eval-*` key, records the model that wrote
the page's content. The judge reads it to warn about self-preference bias when it matches the judging
model.

```yaml
---
title: Installation
evals:
  - use: no-future-promises
  - id: install-command-present
    assertion: The page contains a bash code block with `npm i -g doc-detective`.
    grader: command
---
```

```yaml
---
title: Concepts
eval-suite: how-to
eval-skip: false
evals:
  - use: no-future-promises
---
```

## Entry forms

An entry in the `evals` list takes one of three forms.

**A bare string** is an assertion, judged by AI at error severity. It is the one form with no id of
its own, which is the trade for being one line.

```yaml
evals:
  - The documented install command matches the current package name.
```

A single assertion needs no list at all:

```yaml
evals: The documented install command matches the current package name.
```

:::caution[This changed]
In the 0.1 schema a bare string *referenced* a config-defined eval. It is an assertion now, so a
page that still says `- fresh-enough` no longer runs the freshness grader. It sends those words to
the judge. moose-docevals warns when a string shorthand matches a defined eval id, but the fix is
yours: write `use:`.
:::

**A reference with overrides** narrows a named eval for this page only:

```yaml
evals:
  - use: fresh-enough
    severity: warning
    options: { max-age-days: 180 }
```

| Override | Effect |
|---|---|
| `type` | Replaces the eval's type. |
| `severity` | Replaces the severity. |
| `options` | **Merged** over the base options, not replaced. |
| `skip` | Skips this one eval on this page. |

## `target` selects which bytes are graded

`evidence` tells the judge where to look *within* what it is given. `target` decides what it is
given in the first place, which is why deterministic graders honour it too. A regex grader has no
focus, it has a target.

| Value | What the grader receives |
|---|---|
| `body` (default) | The page body, frontmatter stripped and MDX noise removed. |
| `raw` | The file verbatim, frontmatter included. |
| `frontmatter` | The parsed frontmatter alone. |
| `{source: file, path: <rel>}` | A companion file, resolved against the page's directory. |

```yaml
evals:
  - id: has-an-owner
    grader: tool:regex
    target: frontmatter
    options:
      pattern: "^owner:"
```

A target that cannot be read is an **error**, not a quiet fall back to the page body. A verdict
about the wrong bytes is worse than no verdict. A companion path may not be absolute and may not
climb out of the page's directory.

**An inline definition** declares an eval that exists only on this page. It requires an `id`, kebab-case and unique on the page, and takes every field below. Ids are required rather than derived
from position, because a position-derived name orphans every cached verdict as soon as entries move.

## Eval fields

| Field | Type | Default | Notes |
|---|---|---|---|
| `assertion` | string | none | Required when `grader` is set. The claim about the page that is true or false. |
| `type` | `regression` \| `capability` | `regression` | Most evals guard behavior that must keep working. |
| `grader` | string | `ai` | `ai`, `command`, `human`, or `tool:<name>`. It is `ai`, not `llm`, because the judge may be an agent rather than a bare model. |
| `provider` | string | config default | Which configured provider or agent judges this `ai` eval. |
| `model` | string | config default | Which model judges this `ai` eval, within `provider`. A CLI `--model` still wins. Use it to name a stronger judge for an eval that matters, or a judge other than the model that wrote the page. |
| `runs` | integer 1–50 | `judge.ensemble-runs` | Ensemble runs for this eval alone. A CLI `--runs` still wins. Capped because it multiplies judge cost directly. |
| `evidence` | string | none | Scopes what the judge looks at **within** what is graded. A hint, not a selector; see `target`. |
| `target` | see below | `body` | Which bytes the grader receives. |
| `examples.pass` / `examples.fail` | string or string[] | none | Pins the boundary; one anchor or several. An inline ai eval without them raises a warning. |
| `command` | string[] | none | For `command` graders. `{file}` expands to the page's absolute path. |
| `success-exit-codes` | integer[] | `[0]` | Exit codes treated as a pass. |
| `timeout-ms` | integer ≥ 1 | grader-specific | |
| `generated-assertion-hash` | string | none | Written by script generation, always beside `command`; a mismatch means the script is stale. |
| `options` | object | `{}` | Grader-specific. See [Graders](/moose-docevals/reference/graders/). |
| `severity` | `error` \| `warning` \| `info` | `error` | Only `error` findings fail the build. |
| `weight` | number > 0 | `1` | How much this eval moves its suite's pass rate. It does **not** change the eval's own pass/fail. Zero is rejected, because a weightless eval is a silent disable, and `skip` already means that, loudly. |
| `severity-map` | object | none | Maps a tool's own severities onto moose-docevals severities. |

## Resolution order

For each page, the plan is built in this order:

1. **Suite evals** from the config, via the page's `eval-suite` or `defaults.suite`.
2. **Page entries**, in document order. A reference merges onto the suite's version of that eval; an
   inline definition replaces it.

**Page entries win on id collision.** Local override beats global default, which is the right
behavior and invisible until it bites. Check the resolved plan with `moose-docevals list` rather than
by running.

Every resolved eval records its `source` as `config` or `page`, which `list` prints.

## Page problems

These are reported per page rather than thrown, so one bad page does not stop the run:

| Problem | Level |
|---|---|
| Frontmatter fails schema validation | error |
| Unknown suite name | error |
| Unknown eval reference | error |
| Duplicate eval id on one page | warning |
| Unrecognized `eval-*` or `cite-*` page key | error |
| String shorthand matching a config eval id | warning |
| Inline ai eval with no `examples` | warning |
| Duplicate citation id, across frontmatter and inline comments | error |
| A `cite:` comment that is neither an id nor `key=value` tokens | error |
| An inline citation with a misspelled field, or a `src` that does not parse | error |
| Citations declared, but no `tool:citations` eval applies to the page | warning |

Errors carry the source line, resolved through docmeta's JSON-Pointer line map, or the line of the
body comment.

## `cites`

A citation pins the source lines a sentence depends on, so
[`tool:citations`](/moose-docevals/reference/graders/#toolcitations) can say when they move, change,
or vanish. The walkthrough is [Cite your sources](/moose-docevals/evals/cite-your-sources/). Two
forms, one vocabulary.

**In frontmatter**, under `cites`, with a body comment naming the entry by id:

```yaml
cites:
  - id: node-floor
    src: scripts/install.sh:3-4
    sha256: 9f2c…e41a
    commit: 4d1e7c0
```

```markdown
<!-- cite: node-floor -->
The installer needs Node 22 or later.
```

**Inline**, as the same fields written as `key=value` tokens in the comment, with no frontmatter:

```markdown
<!-- cite: src=scripts/install.sh:3-4 sha256=9f2c…e41a commit=4d1e7c0 -->
The installer needs Node 22 or later.
```

In `.mdx` the comment is `{/* cite: … */}`, because MDX forbids HTML comments. A comment whose only
token has no `=` is a reference; anything with `key=value` tokens is an inline citation. Inline
entries are validated against the same definition as the list, so a misspelled field is the same
error in both forms. The comment goes on the line above the sentence or at the end of it; that
sentence is the **claim** findings quote. Comments inside fenced code blocks and inline code spans
are ignored, which is how this page can show the syntax.

| Field | Type | Notes |
|---|---|---|
| `id` | kebab-case | Required on a frontmatter entry; optional inline (`id=`). Unique per page across both forms. |
| `src` | string | Required. See the grammar below. |
| `sha256` | 64 hex characters | Hash of the cited lines under the rule below. Absent means **unminted**: `cite refresh` fills it, and `run` reports it rather than passing. |
| `commit` | 7–40 hex characters | Commit the hash was minted at. Overrides `cite-commit`. Enables the commit subjects in a `changed` finding and the never-true check. |
| `quote` | boolean (`false`) | The page reproduces the cited lines verbatim in the first fenced code block after the comment; the grader compares the copy too. Inline, the bare token `quote`. |

An all-digit `sha256` or `commit` must be quoted in YAML, or the parser reads it as a number. The
writers quote it for you; the error names the fix if you write one by hand.

**`src` grammar.** A range is `:L` or `:L1-L2`, 1-based and inclusive. No range means the whole
file.

| Form | Example | Read as |
|---|---|---|
| Relative path | `scripts/install.sh:3-4` | A file relative to the directory moose-docevals runs in, normally the repository root, so a moved page keeps its citations. |
| Absolute path | `/srv/shared/spec.md:10-20` | That file. Not portable across machines. |
| GitHub file URL | `https://github.com/o/r/blob/main/src/x.ts#L3-L9` | The raw file at that ref. A ref that is a commit never drifts; a branch tracks. |
| Other https URL | `https://example.com/spec.txt:5-9` | Fetched as is. |

**Hashing rule**, so any script mints the same hash. Read as UTF-8 and strip a byte-order mark.
Normalize line endings to LF. Take lines L1..L2 inclusive and join them with LF, with no trailing
newline and trailing whitespace preserved. `hashRange` is exported from the package for scripts that mint
elsewhere.

## `eval-provenance`

The durable record of which evals a machine proposed, and how sure it was. `moose-docevals fill`
writes one entry per model; a **human deletes the entry** once those evals are reviewed, so a
surviving entry means unreviewed machine-proposed evals.

```yaml
---
title: Install the operator
eval-provenance:
  - generated-by: claude-fable-5
    evals: [install-verified, eks-coverage]
    confidence:
      install-verified: 0.88
      eks-coverage: 0.74
evals:
  - id: install-verified
    assertion: The Helm install steps produce a Ready operator pod.
---
```

| Field | Type | Meaning |
|---|---|---|
| `generated-by` | string | Required. The model or agent that proposed the evals. |
| `evals` | string[] | Ids it proposed. |
| `confidence` | object | 0–1 per eval, keyed by the same ids. |

A second `fill` run by the same model extends its existing entry rather than adding a near-duplicate.
A different model gets its own.

## Validating the frontmatter itself

The schema ships in the package, so any JSON Schema validator can check your pages:

```bash
docmeta validate --schema node_modules/moose-docevals/schemas/frontmatter-1.2.0.json docs/
```

Or wire it in as an eval, so bad declarations fail the run like any other check:

```yaml
docevals:
  evals:
    frontmatter-valid:
      assertion: Page frontmatter matches the moose-docevals schema.
      grader: tool:docmeta
      options:
        schemas: ["node_modules/moose-docevals/schemas/frontmatter-1.2.0.json"]
      severity: error
```

Programmatic consumers can import the schema object or its resolved path:

```js
import { frontmatterSchema, frontmatterSchemaPath } from "moose-docevals";
```
