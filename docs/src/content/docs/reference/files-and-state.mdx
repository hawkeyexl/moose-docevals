title: Files and state
description: What moose-docevals writes, where, and which of it belongs in version control.
---

moose-docevals writes to four places. Only one of them is source you review.

| Path | Default | Commit it? |
|---|---|---|
| `{docDir}/moose-docevals/*.mjs` | generated check scripts | **Yes** — ordinary source |
| `.moose-docevals/cache/` | judge response cache | No |
| `.moose-docevals/cache/fill/` | raw `fill` proposals | No |
| `.moose-docevals/reviews.yaml` | human verdicts | **Yes** — team state |
| `.moose-docevals/golden/*.yaml` | calibration golden set | **Yes** — team state |

## Generated check scripts

Written parallel to the doc, not into frontmatter, so they show up in pull requests and can be edited
by hand.

```text
docs/
├── installation.mdx
└── moose-docevals/
    └── installation.install-command-present.mjs
```

The path is `<scripts.dir>/<page-basename>.<eval-name>.mjs`, with `{docDir}` in `scripts.dir`
expanding to the page's directory. When `scripts.dir` contains no `{docDir}`, scripts go to
`scripts.config-dir` relative to the config file, named `<eval-name>.mjs`.

Frontmatter records the reference and a hash of the assertion that produced it:

```yaml
    - id: install-command-present
      assertion: The page contains a bash code block with `npm i -g doc-detective`.
      grader: command
      command: [node, moose-docevals/installation.install-command-present.mjs, "{file}"]
      generated:
        assertion-hash: aefaa89e…
```

Edit the assertion and the hash no longer matches, so the script is stale and regenerates rather
than quietly checking the old thing.

## Judge cache

Content-addressed. The key is composed in `src/judge/cache.ts` from, among other things:

- `PROMPT_VERSION` — the judge prompt revision
- a hash of the page body
- a hash of the eval fingerprint (assertion, evidence, examples, type)
- the provider and model

So an unchanged page with an unchanged assertion never re-judges, and **changing any of those
invalidates the entry** rather than serving a stale verdict. That is what makes repeat runs
approximately free — see [Caching and turn budgets](/moose-docevals/ci/cost-and-caching/).

`fill` caches raw proposals in `fill.cache-dir` **before** the confidence gate is applied, keyed with
`FILL_PROMPT_VERSION`. Re-running at a different `--confidence` therefore costs nothing.

## `.moose-docevals/reviews.yaml`

One entry per (file, eval) pair. Recording a verdict replaces any existing entry for that pair.

```yaml
- file: docs/install.md
  evalName: explains-why-before-how
  contentHash: 9f2b1c…
  verdict: pass
  reviewer: priya
  date: 2026-08-03
  note: The motivation is in the intro paragraph, not a heading.
```

`contentHash` is a sha256 of the **page body** at review time. A review applies only while that hash
matches; when the page changes, the review is silently ignored and the eval returns to
needs-review. That self-invalidation is what makes persistence safe rather than a way to accumulate
stale approvals.

## `.moose-docevals/golden/*.yaml`

Human-verified cases for [calibration](/moose-docevals/judge/calibrate/). A list of expected verdicts:

```yaml
- file: test/fixtures/pages/docs/get-started/concepts.md
  eval: defines-core-terms
  expected: pass
  rationale: Test specification, test, and step each have a heading and definition.
```

`rationale` is for the humans maintaining the set; it is not sent to the judge.

## Gitignore

The caches are disposable; the reviews and golden set are not. A minimal `.gitignore`:

```text
.moose-docevals/cache/
```

Ignoring `.moose-docevals/` wholesale also discards `reviews.yaml` and the golden set, which are the two
pieces of state your team actually built by hand.
